# 풀이 피드백

출력 형식은 사용자가 정해둔 것을 따른다. 바꾸지 않는다.

1. 분석과 팁을 **불릿 리스트(-)로 쭉 나열**한다. 섹션 헤더(`##`)나 카테고리 구분 없이 불릿만 쓴다.
   시간복잡도 개선 포인트, 불필요한 자료구조, 변수 스코프, 설계 팁을 하나의 리스트에 합친다.
2. 리스트 끝에 **개선된 코드를 코드 블록 하나**로 보여준다.

그리고 코드 블록 뒤에 **기록용 한 줄**을 붙인다(아래 "기록 태깅" 참조).

## 지적하지 않는 것

- **`static` 필드·변수 사용.** 코딩테스트는 단일 실행이라 실무만큼 위험하지 않다.
  사용자가 명시적으로 지적하지 말라고 했다. 단, 여러 테스트케이스 간 상태가 실제로 새서
  답이 틀리는 경우는 `static`과 무관한 로직 버그이므로 지적 가능하다.
- 변수명·포맷팅·주석 스타일. 제출용 코드다.
- 실무 설계 원칙(계층 분리, 예외 타입, 불변성). 맥락이 다르다.

## 우선순위 — 위에서부터 본다

**1. 정답성.** 반례를 직접 만들어 돌려본다. 빈 입력, 원소 1개, 전부 같은 값, 최솟값/최댓값,
음수, 정렬 이미 된 입력. 반례를 찾았으면 그걸 맨 위 불릿에 입력값과 함께 적는다.
추측으로 "틀릴 수 있다"고 쓰지 않는다 — 실제로 실행해 확인한다.

```bash
cd ~/willy/GitHub/daily-algo && java src/main/java/daily/D....java
```

**2. 시간복잡도.** 현재 복잡도를 n의 식으로 쓰고, 문제 제약의 최대 n을 넣어 연산 횟수를
계산한다. 1초 ≈ 1억 연산이 기준선이다. 통과 여부를 숫자로 말한다 — "느릴 수 있다"는 피드백이
아니다.

**3. Java API 선택.** 여기서 실전 점수가 가장 많이 샌다. 자주 나오는 것:
- `String +=` 루프 → `StringBuilder` (O(n²) → O(n))
- `Arrays.sort(int[])` 최악 O(n²) 퀵소트 → 적대적 입력 우려 시 `Integer[]` 박싱 후 정렬
- `list.remove(0)` → `ArrayDeque.pollFirst()`
- `Stack`/`LinkedList` → `ArrayDeque`
- `map.get` 후 null 체크 → `getOrDefault` / `merge` / `computeIfAbsent`
- `contains`를 `List`에 → `HashSet`
- 정렬 기준 비교에서 `a - b` → 오버플로 시 `Integer.compare(a, b)`
- 입력 크기 큰 문제에서 `Scanner` → `BufferedReader`

**4. 자료구조.** 맞는 답이지만 더 적합한 구조가 있으면 교체 근거를 복잡도로 제시한다.

**5. 설계.** 중복 루프 합치기, 조기 종료, 불필요한 전체 정렬 제거.

## 개선 코드 규칙

- 사용자 코드의 **구조와 접근법을 유지**한 채 지적한 부분만 고친다. 전면 재작성은
  학습이 되지 않는다 — 자기 코드가 어떻게 나아졌는지 비교할 수 없기 때문이다.
- 접근법 자체가 틀렸다면(예: DP가 필요한데 그리디) 다시 쓰지 말고, **왜 현재 접근으로는
  안 되는지 반례로 보여주고 멈춘다.** 사용자가 다시 설계할 기회를 준다.
- 개선 코드도 `ALL PASS`가 나오는지 실제로 실행해 확인한 뒤 보여준다.

## 기록 태깅

코드 블록 뒤에 한 줄로 붙인다. `algo-daily` 8단계가 이 값을 그대로 `--errors`에 쓴다.

```
기록: --errors 복잡도오판,API미숙  (판정 근거: naive O(n²)로 n=10만 → 100억 연산 / String += 루프)
```

8종 중에서만 고른다: `유형미인지` `복잡도오판` `경계조건` `자료구조선택` `구현실수`
`문제오독` `API미숙` `수학오버플로` (정의는 `data/types.json`의 `error_causes`).

**최종 정답이어도 과정에서 틀린 게 있으면 태깅한다.** 두 번 오답 후 정답, 중간에 막힌 지점,
반례로 뒤늦게 고친 부분 모두 해당한다. 정답 여부보다 과정의 실수가 실제 약점이고,
그걸 적어두지 않으면 다음에 같은 실수를 반복한다.

완전히 깔끔했다면 `기록: --errors 없음 (첫 제출 정답, 목표시간 내)`로 적는다.
억지로 원인을 만들지 않는다.
