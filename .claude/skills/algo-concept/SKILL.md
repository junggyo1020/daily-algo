# 개념 설명

사용자는 **문제를 풀기 전에 개념을 반사신경 수준으로 박아넣고, 그 다음 문제로 검증**하는 방식을
선호한다. 그래서 이 설명의 품질 기준은 "읽고 이해됐다"가 아니라 **"설명을 덮고 백지에 골격을
직접 쓸 수 있다"**다.

## 절대 규칙: 문제 힌트 금지

개념 설명에 **그날 풀 문제에 대한 어떤 단서도 섞지 않는다.** 섞으면 그날의 측정값이 오염되고,
`유형미인지`를 스스로 극복하는 훈련 기회가 사라진다. 구체적으로 금지되는 것:

- "이 문제는 ~로 풀면 된다", "오늘 문제에선 ~를 주의해라"
- 그날 문제의 입력 크기·제약을 인용한 복잡도 계산
- 그날 문제와 유사한 기출 문제 이름 제시
- 예시 코드에 그날 문제의 변수명·도메인을 쓰는 것

예시는 **개념 자체를 보여주는 중립적 예시**(배열 [1,2,3], 격자 3×3 등)로만 든다.

## 설명 순서 — 6단계

순서를 바꾸지 않는다. 비유 없이 정의부터 들어가면 추상적으로 남고, 함정을 먼저 말하면
개념이 어렵게 느껍진다.

**1. 비유 (2~3문장)**
일상의 물건·행동으로 먼저 감을 잡게 한다. 예: 누적합 = 가게 매출을 날마다 더해 적어둔 장부,
어느 구간 매출이든 두 날짜의 누계를 빼면 바로 나온다.

**2. 정의**
한 문장으로 정확하게. 용어를 쓰면 그 용어도 그 자리에서 풀어준다.

**3. 공식 / 점화식 / 골격 코드**
Java로 쓴다. 외워야 할 최소 골격을 명시한다. DP라면 **상태 정의 → 점화식 → 초기값 → 순회 순서**
4줄을 따로 적는다. 이 4줄이 DP의 전부다.

**4. 시간복잡도 이득 — 왜 이걸 쓰는가**
순진한 방법과 나란히 둔다. "naive O(n²) → 이 방법 O(n log n)", 그리고 n=100,000일 때
실제 연산 횟수 차이를 숫자로 보여준다. 이 숫자가 "왜 이 개념이 필요한가"의 유일한 답이다.

**5. 언제 떠올려야 하는가 — 신호**
가장 중요한 단계다. 코딩테스트 실패의 대부분은 개념을 몰라서가 아니라 **꺼내지 못해서** 발생한다.
문제 문장에 나타나는 신호를 구체적으로 나열한다.
예(이진탐색): "최소/최대를 구하라 + 어떤 값으로 가능 여부 판정이 쉽다" → 파라메트릭 서치.
예(누적합): "구간 합을 여러 번 묻는다", "쿼리가 10만 개".

**6. 흔한 함정**
Java 특유의 것을 포함한다 — `int` 오버플로, `Arrays.sort`의 원시타입 최악 O(n²),
`substring` 비용, `HashMap` 순서 보장 없음, 방문처리 시점 등.

## 길이와 깊이

8분 안에 읽히는 분량을 목표로 한다(대략 500~900자 + 골격 코드). 초과하면 6단계 중
**5번(신호)과 6번(함정)을 남기고** 1~4를 압축한다 — 그 둘이 실전 점수에 직결된다.

이미 터치한 유형의 리마인드라면 전체를 다시 쓰지 않는다. `data/types.json`의 해당 유형
`concepts` 체크리스트를 보여주고 **"이 중 설명 못 하겠는 항목"**을 사용자가 고르게 한 뒤
그것만 깊게 설명한다. 이게 보강 단계의 기본 운영 방식이다.

## 보조 개념

한 문제가 두 개념을 함께 요구하는 경우(누적합+투포인터, 이진탐색+그리디 판정 등)
보조 개념도 같이 짚되 **순수 개념 수준으로만** 한다. "이 둘을 함께 쓰면 ~ 문제가 풀린다"는
조합 설명은 힌트이므로 넣지 않는다.

## 검증

설명 끝에 질문 한 개를 던진다 — 개념만으로 답할 수 있고, 그날 문제와 무관한 것.
예: "n=10만이고 구간 합 질의가 10만 번이면, 누적합을 안 쓰면 총 몇 번 연산인가?"
답을 못 하면 4번(복잡도)으로 돌아간다.
